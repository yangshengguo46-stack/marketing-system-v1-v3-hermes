## 一、按目标倒推的四大真实缺口

按"桌面端第一版可试用"和"完整产品"两个目标倒推，当前只有四类实质缺口：

| # | 缺口 | 影响进度 | 现状 | 阻塞点 |
|---|---|---|---|---|
| G1 | **精确任务恢复与结构化计划**（P0-02/03） | 对话/任务 72%→90% | plan 是启发式文本猜测；`checkpoints_enabled=False`；跨进程恢复靠 resume prompt | 原被"不改 Hermes 上游"卡住 → **已解锁**，可在 Hermes agent loop 内做确定性 plan/step checkpoint |
| G2 | **真实发布闭环**（PUB-05/07/09/10） | 发布/复盘 20%→60%+ | 只有本地占位 L3 执行器；无平台 post ID、无指标回收 | PUB-05 抖音发布可行性 ADR **需用户确认路线**（官方接口 / 创作者中心 MCP / 人工确认三选） |
| G3 | **长期学习闭环**（MEM-12~19、P1-01/04/05） | 长期学习 40%→70%+ | 记忆 CRUD/晋升/衰减/回滚全部有地基和测试，但没有真实"发布结果→记忆→策略"回路 | 依赖 G2 产生真实结果数据；MEM-12 PoC 可先行 |
| G4 | **真人验收积压 + 干净机交付**（P0-04~07、MCP-06/07/09、DESK-08/12） | 打包 60%→90% | 自动化全绿，但审批四路径、双账号矩阵、扫码兜底、干净机安装均未真人过 | 只能由用户真人执行；DMG/签名/公证属工程工作 |

其余子台账条目要么是这四类的分解，要么是 P2（微信/飞书、Web 视频、Windows）。

## 三、推荐补齐顺序

1. **G1（立即，Hermes 已解锁）**：RUN-01 结构化 Plan → RUN-02 Hermes 侧真 checkpoint → RUN-04 跨进程恢复回放测试。这是"61%→可信 Agent"的最大单项。
2. **并行工程线**：MCP-13 切流收尾 + MCP-10 一致性测试 + DESK-03 secret scanner（无依赖、纯自动化）。
3. **G2 解锁决策**：用户确认 PUB-05 ADR 路线（建议先做 ADR 三路对比稿供拍板）。
4. **真人验收批次**：攒齐 MCP-06/07/09 + RUN-08 + P0-01 口令做一次集中真人验收，一次覆盖多个台账的"待真人"项。
5. **G3**：G2 出真实数据后接 MEM-13~15；MEM-12 PoC 可穿插。
6. **G4 交付**：DESK-08 干净机 → DESK-12 签名公证 → 更新/卸载。

## 四、Hermes 源码修改纪律（2026-07-10 已废止的旧纪律）

- 历史做法是只允许少量 runtime patch，并把产品主链放在 `engine/agent_core` adapter；该做法已经造成套壳架构，禁止继续。
- 新口径：Marketing OS 是 Hermes 产品 fork，UI 与底层均可直接重构；领域服务可以模块化存在，但 Agent 生命周期必须归 fork 原生执行链所有。
- 仍保留回归测试、数据迁移、安全边界和提交可审计性；这些用于保证质量，不用于阻止必要的源码改造。
