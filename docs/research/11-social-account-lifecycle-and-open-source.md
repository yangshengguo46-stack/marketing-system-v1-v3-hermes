# 社交媒体账号全生命周期与开源方案调研（2026-07-03）

## 一、产品结论

市面上多数开源社媒产品覆盖的是“生产—排期—发布—看数”，本项目要拥有的是一个持续循环：

`商业目标 → 目标受众假设 → 市场/对标证据 → 定位与账号 DNA → 内容实验 → 发布 → 真实受众与结果 → 差距诊断 → 策略修订 → 规模化`

它不是一次性起号问卷。账号定位、受众判断和内容策略都必须有版本、证据和生效时间，并随着真实结果修订。

## 二、从 0 到持续经营的完整流程

| 阶段 | 核心问题 | 输入 | 产物 | 退出条件 |
|---|---|---|---|---|
| 0. 经营约束 | 为什么做、卖什么、由谁生产、风险边界是什么 | 商业目标、资源、合规边界 | 目标、约束、北极星指标 | 用户确认目标和不可做事项 |
| 1. 目标受众假设 | 希望吸引谁、解决什么问题 | 用户经验、产品/服务信息 | `target_audience_hypothesis v1` | 画像、需求、场景、反画像均明确 |
| 2. 市场与对标 | 这些人正在看谁、为什么看 | 平台搜索、热点、对标账号和样本 | 对标集合、内容模式、空位判断 | 至少形成可追溯的正/反例 |
| 3. 定位与 DNA | 我们凭什么被选择 | 前两阶段证据 | `account_positioning_version v1`、内容支柱、语气、禁区 | 用户批准定位版本 |
| 4. 内容实验设计 | 什么最值得先验证 | 定位、平台规则、对标样本 | 选题矩阵、假设、预测、发布节奏 | 每条内容有可证伪假设和指标 |
| 5. 冷启动执行 | 能否稳定产出并获得初始信号 | 内容资产、授权、排期 | 发布回执、异常、样本量 | 达到约定周期/内容量，而非单条爆款 |
| 6. 真实受众观察 | 实际吸引来的到底是谁 | 创作者中心/API、互动、评论、留存 | `actual_audience_snapshot` 时间序列 | 来源、窗口、缺失字段明确 |
| 7. 结果与差距诊断 | 目标、对标、实际差在哪 | 内容指标、受众快照、预测 | 归因候选、目标—实际差距 | 能区分事实、推断和未知 |
| 8. 策略修订 | 下一轮该坚持、停止还是试什么 | 诊断、用户反馈、失败记录 | 新定位候选、实验、策略权重 | 重要改变经确认并可回滚 |
| 9. 规模化经营 | 如何稳定增长和变现 | 已验证打法 | 技能、SOP、跨平台变体、商业闭环 | 持续循环，不存在永久完成 |

正确顺序不是“先读现有粉丝画像再定位”。新号没有真实粉丝数据，因此先建立目标受众假设；有账号后再用真实受众快照验证和修订。对标研究也不是照抄，而是寻找已验证规律和未被满足的空位。

## 三、五类受众信息必须分开

| 类型 | 含义 | 可否当事实 |
|---|---|---|
| `target_audience_hypothesis` | 用户希望服务的人群 | 否，是战略假设 |
| `benchmark_audience_observation` | 对标账号公开内容和互动体现的人群 | 只能作为外部观察 |
| `actual_audience_snapshot` | 平台官方/API/创作者中心给出的本账号画像 | 是带时间窗的一方事实 |
| `audience_inference_candidate` | 从评论、语言、行为推断的年龄/兴趣等 | 否，必须标置信度和样本偏差 |
| `account_positioning_version` | 综合以上证据作出的经营决策 | 是决策，不是客观事实 |

职业、收入、购买力等字段若平台没有提供，必须显示“暂无数据”；模型不能补齐。评论关键词只能描述“参与评论的样本”，不能外推为全部粉丝画像。

## 四、官方能力边界

抖音开放平台的“获取用户粉丝数据”接口可返回性别、年龄、地域等分布，但需要申请 `fans.data` 权限和用户授权；首次授权约两天后数据才完整，并且只向粉丝数大于 100 的用户提供。架构上应以官方 OAuth/API 为长期主通道，MCP/创作者中心为用户可见的补充通道，两者写入同一标准快照，来源等级不同。

## 五、开源方案对照

| 项目 | 强项 | 不解决什么 | 本项目结论 |
|---|---|---|---|
| Postiz | 渠道 adapter、排期、发布队列、指标 | 起号逻辑、受众假设、对标到定位的决策链 | C：参考 provider/receipt/analytics 结构，不复制 AGPL 代码 |
| Postiz Agent | device auth、CLI/MCP、账号与帖子指标、JSON 输出 | 账号战略和长期学习 | C：参考 Agent 工具粒度、回执与缺失 ID 恢复 |
| BrightBean Studio | workspace、审批、排期、发布、监控 | 国内平台和账号定位闭环 | C：参考运营工作台与审批体验 |
| TryPost | brand profile、工作区、发布、账号分析、MCP/API | brand profile 仍是静态配置，不是证据驱动的 DNA | C：参考品牌隔离和 MCP/REST 边界；AGPL 不嵌入 |
| Mixpost Lite | 多账号、内容日历、排期、平台数据分析 | 起号研究与定位版本 | C：参考平台能力差异和队列；Lite/Pro 边界需固定版本复核 |
| MediaCrawler | 多平台字段、登录与页面适配、失败案例丰富 | 商用许可、稳定官方通道、账号战略 | X/C：许可明确限制商业使用；只研究字段和失败模式，不复制、不打包 |

开源生态证明“生产与发布层”已有大量成熟参考，但没有一个候选能直接提供本项目需要的全周期账号大脑。真正的差异化数据——目标受众、定位版本、实验、实际受众快照、拒绝和修订历史——必须由本项目掌握。

## 六、对现有项目的判断

### 可直接复用

- Hermes 长任务、checkpoint、审批和工具循环：负责跨天推进生命周期任务。
- account-scoped MCP：负责用户授权后的平台可见操作和补充采集。
- `benchmark_accounts` / `benchmark_samples`：作为对标领域的初始表，但需补归属、来源和观察窗口。
- 内容资产、评分、盲预测、发布回执、指标回收、复盘：组成内容实验闭环。
- memory candidate 治理：保存可检索的偏好与经验，不承担业务真相源。

### 必须修改

1. 新增项目拥有的 `AccountLifecycleService`，作为账号经营状态的唯一编排入口。
2. 新增版本化、结构化的受众假设、受众快照、定位版本和实验；不能继续塞进 YAML、metadata JSON 或记忆 prose。
3. 对标账号必须绑定目标账号/经营项目，并保存来源、采集时间、证据和选择理由。
4. 现有 `audience_persona.py` 降级为“推断候选生成器”；不保存代表性原评论到长期 DNA，不把关键词命中当年龄事实。
5. `user-profiles.yaml` 只做旧配置迁移输入，逐步退出运行时真相源。
6. Agent 每次给建议时要说明依据来自目标假设、对标观察、真实快照还是推断；数据不足时主动建立采集/实验任务。

## 七、采用纪律

- API、MCP、公开网页、用户输入、模型推断全部写统一 provenance，但信任等级不同。
- 所有观察至少有 `source_kind/source_ref/captured_at/window_start/window_end/confidence/data_gaps`。
- 结构化事实是主数据；记忆是带 scope 的检索副本；向量索引不是事实库。
- 定位修订、自动发布和平台副作用继续经过现有审批/授权边界。
- 不以“抓到了页面”冒充官方 API，不以“生成了画像文案”冒充了解用户。
